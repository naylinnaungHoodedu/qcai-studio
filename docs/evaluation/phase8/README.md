# Phase 8 engineering evidence

`run_invariance_harness.py` exercises the actual two-pass pipeline with three deterministic presentation choices, fresh caches and the pinned fake gateway in shadow mode. It hashes the retrieval and evidence objects and compares locked and delivered claims, citations, and final V1/V2 outcomes. The F-2 scan covers typed payloads and the governing configuration. These public fixtures provide engineering evidence. E3 and LQ-1 require separate research evidence.

Exit 0 means the run passed. Exit 1 marks committed report drift, exit 3 marks an invariant or presentation-variation stop, and exit 4 refuses a dirty-tree write. A run with `--stop-sqlite` and an explicit existing development database also sets its shared adaptation stop. The operator clears that stop explicitly with `--clear-stop-sqlite`. For the configured API database the operator uses `python -m app.workers.learner_planner status`, `stop --reason invariance`, or `clear --confirm` as described in the Phase 8 deployment runbook. A check without a database argument runs in isolation. `--items` accepts a JSON list drawn from approved fixture questions and `--design two-pass` selects the engineering design.

`prove_erasure.py` builds isolated SQLite schemas for four principal types, plus bound and claimed accounts. It independently checks the target and control rows and verifies the retained receipt digest. Exit 0 means the proof passed, exit 1 marks committed report drift, exit 3 marks a failed proof, and exit 4 refuses a dirty-tree write. The report contains table names and counts. It excludes user identifiers and receipt tokens.
