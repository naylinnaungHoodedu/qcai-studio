# Deploying by digest, with a committed deployment record (plan task 1.9, AC-1-7)

AC-1-7: "A committed deployment record names digest and commit; /health returns that commit."

**Not run yet.** A rollout is a production change. It needs the Platform Owner's approval and a D-05 release approval, and it is currently blocked by DL-2 (D-02/D-31). Images are built by Cloud Build, never on a workstation. Deploy the API and the frontend together: they share `GUEST_TOKEN_SECRET`.

## 1. Build one commit, in Cloud Build
Build from a clean checkout of the exact commit on `main`, so that what is uploaded is that commit:

```bash
GIT_LFS_SKIP_SMUDGE=1 git clone https://github.com/naylinnaungHoodedu/qcai-studio.git build-src
cd build-src
git checkout <commit>
git status --porcelain   # must print nothing
gcloud builds submit --project naylinnaung --config infra/cloudbuild/api-image.yaml --substitutions _GIT_SHA=$(git rev-parse HEAD) .
gcloud builds submit --project naylinnaung --config infra/cloudbuild/frontend-image.yaml --substitutions _GIT_SHA=$(git rev-parse HEAD) .
```

Source assets are not part of the build: `.gcloudignore` and `.dockerignore` keep them out of the upload and the image (AC-1-5; P1-D-07). Each image is tagged with the commit (never `:latest`) and stamped with it, so `/health` reports it. Cloud Build records each pushed digest. A missing or short `_GIT_SHA` stops the build.

## 2. Deploy by digest, check, then move traffic
```bash
python scripts/deploy_by_digest.py --service qcai-api --commit <commit>             # the plan only
python scripts/deploy_by_digest.py --service qcai-api --commit <commit> --execute --no-pin --update-secret GUEST_TOKEN_SECRET=qcai-guest-token-secret:1
python scripts/deploy_by_digest.py --service qcai-frontend --commit <commit> --execute --no-pin --update-secret GUEST_TOKEN_SECRET=qcai-guest-token-secret:1
```

`--update-secret` binds a secret by name and version, never by value. `--no-pin` stops before traffic moves, so the tagged URLs can be checked first; the script then prints the `update-traffic` command. Without it, the script moves traffic as soon as `/health` reports the commit.

With `--execute`, the script:
1. resolves the image digest;
2. deploys it with no traffic and a `c-<commit[:12]>` tag;
3. checks that the tagged URL's `/health` reports the commit. If it does not, it stops with no traffic moved;
4. pins 100% of traffic to that named revision, so traffic no longer follows "latest".

## 3. Record, and commit the record
```bash
python scripts/deployment_record.py --commit <commit> --write deploy/records
```

The record names, for each service:
- the serving revision and its image digest;
- the public `/health` response.

It exits 1 if traffic follows "latest", a digest is missing, or `/health` does not report the commit. Commit a passing record by pull request. That record, plus the `/health` it shows, is the AC-1-7 evidence.

## Rollback
Route traffic back to the previous revision by name, then record again:

```bash
gcloud run services update-traffic qcai-api --project naylinnaung --region us-central1 --to-revisions <previous revision>=100
```

Before the first digest-pinned rollout, the previous revisions are `qcai-api-00036-lzg` (`sha256:e94cadd0…4775a5`) and `qcai-frontend-00051-sw7` (BEP-0, AC-0-2).

Each `tutor.ledger.append_deferred` (ledger latency on the request path) is investigated; it is a stop only when its attempt ends in `tutor.ledger.append_failed`, or, with always-on CPU allocation (or none recorded yet), when it has no terminal line after the 360 s horizon (coverage). The horizon counts every wait the code bounds: the pool's 30 s checkout timeout, the 30 s connect bound that `app.core.db` enforces on a new Cloud SQL connection, the server-side statement, lock and idle-in-transaction timeouts, and the append queue. A later terminal line there therefore means an open database connection stopped answering, and it stays a stop to investigate. When the database host or the network to it is gone, the TCP keepalive `app.core.db` sets on each Cloud SQL connection ends such a read within 60 s of the connection's last traffic, so the attempt's terminal line comes by the 840 s dead-peer horizon (`ledger.dead_peer_horizon_s`). When the server keeps the connection up and never replies, nothing in the code ends the read: it lasts until the process exits, and it holds one of the instance's four append workers meanwhile. A deferred append that ends `appended` within the horizon is not a stop, and with request-based CPU allocation recorded neither is one that ends `appended` later, in any window (spec 4.12).

On a stop:
- For the shadow, set `TWO_PASS_TUTOR=off`.
- **An attempt still without a terminal line 840 s after its `tutor.ledger.attempted` line** (`ledger.dead_peer_horizon_s`; always-on CPU allocation, or none recorded yet) is held by a server that keeps its connection up and never replies. Its worker stays held until the process exits, and four such stalls queue every later legacy append on that instance until the in-flight cap refuses them (`append_failed`). Replace the instance: deploy the same digest as a new revision (sections 1-3) and move traffic to it, with the same D-05 approval as any deploy; setting `TUTOR_LEDGER_ENABLED=false` (below) also deploys a new revision. Then investigate the database, and read `--coverage-since` once the old revision has stopped.
- For legacy appends, investigate the database. If appends are failing, deferred or slowing the request path, set `TUTOR_LEDGER_ENABLED=false`: it is the kill switch for every request-path ledger write. It relaxes an audit control, so it logs a `config.override` event (`tutor_ledger_disabled`) and needs the same D-05 approval as any switch; the turns not recorded meanwhile show in `--coverage-since`.

Legacy deliveries continue either way, because every ledger write fails open.

**Operations** (development, or a recorded `RANKING=shadow` override; in-image, connecting as the API does). The worker's own events (`ranking.status`, `ranking.commissioned`, `ranking.recommissioned`, `ranking.replay_checked`, `ranking.stop_cleared`, `ranking.scan_refused` and the `replay --check` stop) are JSON lines on `qcai.worker`; the scan's events (`ranking.scan`, `ranking.batch`, `ranking.alarm`, `ranking.sustained_alarm`, `ranking.fallback`, `ranking.model_change`, `ranking.promote`, `ranking.demote` and the scan's `state_mismatch` stop) are on `qcai.ranking` (observability.md, Phase 9):
1. **Commission the static generator first:** `python -m app.workers.ranking commission extractive-d19-v1` runs the shadow golden regression over golden-set-v1's 40 queries and records the commissioning prior (alpha = 1 + clean, beta = 1 + failed). The regression itself writes nothing. Recording it appends the `commission` input after what the scan's step 3 would append first: `config` when the log lacks the package's ranking block, `model_seen` for each candidate the log has not seen (so a fresh log gets `config` and one `model_seen` per candidate), `model_change` for a candidate whose version changed, and `availability` only when a candidate's availability differs from the log's (a fresh log where every candidate is available gets none); then a `checkpoint`, and rewrites the derived state (`ranking_states`, `ranking_incumbents`). The image carries the recommission set (`docs/evaluation/phase7/golden_set_v1.json` under `/app`); a missing or changed set refuses the command (exit 2, `ranking.scan_refused` `recommission_set_unavailable`). A commission for a model that already has outcomes is refused (exit 2, `commission_refused` with `refusal` `has_outcomes`) and writes nothing; it also logs no `ranking.model_change` or `v3.x5_event` for a version change its rolled-back transaction saw (the next scan records and logs that change once). Until a static candidate is commissioned the scan consumes nothing and exits 2 (`ranking.scan_refused` `uncommissioned`).
2. `python -m app.workers.ranking scan [--limit N] [--until-done]`: consume ledger records into the ranking event log (`ranking.scan`). Alarms raise the X5 audit through Phase 6 (`ranking.alarm`); an empty eligible set abstains (`ranking.fallback`) and, when V3 is not off, enqueues a V3 item (`ranking_empty_eligible_set`; with V3 off the `select` row notes `v3_off`); a candidate's version change deflates its trust, caps it at C and raises X5 (`ranking.model_change`). A scan that stops the ranking (below, `state_mismatch`) exits 1, with `--until-done` too, so a scripted run reports the stop.
3. `python -m app.workers.ranking status`: `ranking.status` with the SLIs (micro-batch latency, switch rate, fallback rate, cost, ratings, the CUSUM, the skips, the open holds, the stop).
4. After a version change: `python -m app.workers.ranking recommission <adapter>` runs the same regression; a pass (every query of the golden set gives a completed verdict and none fails its first pass) lifts the cap, a fail (a failed first pass, or any query skipped, for example by the daily budget or a detector down) keeps it (exit 1). Time never lifts the cap. A recommission for another version than the model's is refused (exit 2, `recommission_refused`) and writes nothing.

**Holds with V3 off.** A hold (a CUSUM alarm or a model change) lasts until every X5 window raised under it has closed: its own and that of each sustained alarm on the same stream, which opens a later window under the same hold. Closing a window needs V3 draws: with `V3_QUEUE=off` no window closes and promotions stay held. That is the conservative reading (spec conflict 15).

**The stop.** "Flag to static assignment, alarms retained. Stop: a replay mismatch." (plan Phase 9 L). `python -m app.workers.ranking replay --check` takes the ranking lock (as the scan does, so it never reads a half-written log or chains a row beside a running scan) and replays the stored log twice; on a mismatch (the hash chain, a derived event, a checkpoint or the stored state) it appends a `stop` row, logs `ranking.stop` at ERROR on `qcai.worker` and exits 1 (the stop line and the `stop` row carry `mismatch`, what mismatched, and `first_mismatch_seq`), and every later scan is refused (exit 2, `stopped`) and `/ready` reports `ranking.stop.stopped` true. A scan that finds the stored state differing from its checkpoint stops the same way (`state_mismatch`, `ranking.stop` on `qcai.ranking`, exit 1). What clears depends on what mismatched: the `mismatch` of the `ranking.stop` line or `stop` row (`state`, `chain`, `derived`, `checkpoint`, `input:<error>` or `replays_differ`), or `state_mismatch` for the scan's stop. Read it before running `clear-stop`:
- **The stored state only** (`state`, `state_mismatch`): fix the cause (the data, or the code that wrote it), then `python -m app.workers.ranking clear-stop --cause fixed_code|fixed_data|restored_backup`. Under the ranking lock it checks the log itself (the chain, every stored derived event, every checkpoint, and two replays equal), rewrites `ranking_states` and `ranking_incumbents` from the replay and appends a checkpoint and a `clear_stop` row.
- **Two replays differ** (`replays_differ`): the log replays cleanly but the code is not deterministic, so `clear-stop` is refused (exit 2, `ranking.scan_refused` `replays_differ`) until the code is fixed. Fix the non-determinism, deploy the fixed image, run `replay --check` and then `clear-stop --cause fixed_code`. If the fixed code changes the controller's output, the stored derived events now mismatch (`derived`): handle that as below.
- **The log itself** (`chain`, `derived`, `checkpoint`, `input:*`): `clear-stop` is refused (exit 2, `ranking.scan_refused` `log_mismatch` with the `mismatch`), because `ranking_events` is append-only and every later `replay --check` would stop again. Either restore a database backup taken before the mismatch, or archive the log and start a new one: export the four ranking tables (`pg_dump -t 'ranking_*'`), `alembic -x allow_ranking_drop=true downgrade 20261123_phase7_ehmf`, `alembic upgrade 20261123_phase9_ranking`, then commission again (step 1). A release that changes the controller's output (a rule, a parameter rule, a bug fix in the pure modules) makes every stored derived event of an existing log mismatch: archive and start a new log when such a release is deployed (ehmf-change-control.md, the ranking block). Each step is a cloud write under the freeze outside development.

**Rollback.** Set `RANKING=off`: the scan and the hook stop; the event log, the alarms and their X5 windows are retained (nothing is deleted). A digest rollback needs no downgrade: an image before Phase 9 reads no Phase 9 table. It does read `v3_queue_items`, and its V3 queue cannot show or adjudicate an item whose reasons name `ranking_empty_eligible_set`: its queue-reason type predates Phase 9, so the queue listing (any state) and the item read fail validation on such a row, and adjudicating it would too. Such items exist only where the ranking ran in shadow with V3 not off. Before a digest rollback past Phase 9, count them: `SELECT count(*) FROM v3_queue_items WHERE reasons LIKE '%ranking_empty_eligible_set%'`. With none, the digest rollback is safe. With any, keep the Phase 9 image and roll back with `RANKING=off` alone: the queue keeps every item (none can be deleted), so the older image would fail on them for good. A downgrade past the revision, when one is decided, is `alembic -x allow_ranking_drop=true downgrade 20261123_phase7_ehmf` (an absolute target, after `alembic current` shows `20261123_phase9_ranking`, following the Phase 8 downgrade in step 3 of the Phase 3 rollback when starting at the Phase 8 head), and only after `python -m app.workers.ranking status` has logged the log's state: without the flag it refuses while `ranking_events` holds rows.

The settings of this runbook: `RANKING`, `RANKING_SHADOW_GENERATION`, `CONFIG_PACKAGE_PATH`.
